# Design

## Context

See proposal.md for motivation. The obstacle is module readability only, and it was
measured, not assumed (`archive/2026-10-01-support-cross-classloader-proxy/design.md`,
task 1.1): loader, package, and privilege all check out; `Module.canRead` is the sole
false term, and a named module can never read the unnamed module.

The gate already exists. `OpenProxy.requireContractTypesVisible` checks
`root.getModule().canRead(contractModule)` for `Interceptor`, `DispatchTarget`, and
`internal.Rebindable` before any generation, and turns a false term into the
`forModuleRead` diagnostic. Once OpenProxy is a module the target module can
`requires`, `canRead` becomes true and every downstream path (definition, dispatch,
caching by lookup root class, eviction) runs unchanged.

The surface generated bytecode actually references across the library boundary was
audited from the generators, not guessed:

```
owner written into generated class          source
  io/github/lamspace/DispatchTarget          ClassGenerator.java:151 (interfaces[])
  io/github/lamspace/internal/Rebindable     ClassGenerator.java:152 (interfaces[])
  io/github/lamspace/Interceptor             emitted signatures (4 sites)
  io/github/lamspace/ConstructorInterceptor  constructor-interception path
  io/github/lamspace/generator/
      DispatchGenerator.methodDispatchHash   DispatchGenerator.java:133 (INVOKESTATIC,
                                             overload-disambiguation branch)
```

Three packages. Any packaging choice that hides `internal` or `generator` must either
export them anyway or move these reference points — that constraint drives D1.

## Goals / Non-Goals

**Goals:**
- Make named-module targets proxyable through a standard JPMS edge (`requires`),
  with zero new API surface.
- Give the artifact a stable module name on the module path (a hygiene win for every
  module-path deployment, independent of P3's scenario).
- Keep every classpath runtime byte-for-byte identical, so the 249 existing tests,
  the published benchmark numbers, and the 22fdffb guards mean what they mean today.

**Non-Goals:**
- Hiding `io.github.lamspace.internal` / `io.github.lamspace.generator` from module
  readers. On the classpath they were never protected; JPMS enforces nothing a
  classpath user can't already reach, and the honest-export variant is D1's rejected
  alternative, not a TODO.
- `opens`/service-registration polish, `--add-reads` documentation beyond naming the
  workaround, OSGi (module names are orthogonal to bundle metadata).
- Retiring `jpms-strong-encapsulation`'s fail-fast behavior for JDK-internal targets;
  strong encapsulation and readability are different gates.

## Decisions

**D1: `Automatic-Module-Name` (option A), not a real `module-info.java` (B), not
documenting `--add-reads` only (C).**
- B's only net gain over A is declaring `requires org.objectweb.asm` so ASM enters the
  graph through the requires edge; A relies on ASM being rooted or required by the
  deployment (measured in task 1.1 before anything else lands). B pays for that with
  the export audit above — it must unqualified-export all three packages, or relocate
  `Rebindable`/`methodDispatchHash` into an exported `spi` package (a redesign, more
  than P3's scope). Export-everything-as-automatic and export-everything-as-named give
  the same visible surface, so B's "honest boundary" is notional unless paired with
  relocation. B additionally flips maven-surefire 3.x into module-path test execution
  the moment `module-info.class` appears in `target/classes` (needs a pinned
  `<useModulePath>false</useModulePath>` and re-validation of all 249 tests + the
  release pipeline), and levies a permanent tax: every future package the generators
  touch must be added to the exports list, with failure visible only in named-module
  deployments.
- C keeps the matrix cell empty and asks users to launch with a flag that says the
  library is not a module.
- A is a one-line manifest entry: zero effect on classpath runtimes, exports-all is
  acceptable here because the generated bytecode needs those packages anyway.
- Revisit condition recorded: if task 1.1 measures that ASM graph membership is
  practically impossible without a `requires` edge (beyond ordinary module-path
  deployment shapes), B returns to the ROADMAP as its own change.

**D2: Module name `io.github.lamspace.openproxy`** (groupId.artifactId). Without any
declaration the derived name comes from the file stem (`openproxy-0.2.0`), which
changes per release and breaks `requires` stability — the hygiene half of this change.

**D3: `forModuleRead` becomes remedy-preserving, not behavior-preserving-text.**
Keep naming both modules and the readability statement (the existing test asserts
`cannot read module` and the module name — both stay); replace the "OpenProxy is
currently published as a classpath artifact ... until it ships a module declaration"
sentence, which is false after this change, with the two-step remedy. The scenario for
classpath deployment is unchanged in kind, so `cross-classloader-proxy` specs stay
valid; this is why the delta is a new capability, not a modification.

**D4: Test harness = in-process module layer, artifact-synthesized shape.**
`NamedModuleFixture` already defines `com.acme.mod` as a real named module via
`ModuleFinder.of(mods)` + `defineModulesWithOneLoader` against the boot layer.
The success-path fixture extends the finder to two more roots:
- an **openproxy.jar synthesized from `target/classes`** with the
  `Automatic-Module-Name` manifest entry written by `java.util.jar` — the exploded
  directory cannot carry a manifest, so the test must exercise the shipped form;
- the **asm.jar located via**
  `ClassWriter.class.getProtectionDomain().getCodeSource().getLocation()` (present on
  the test classpath).
A new resource module `com.acme.proxyable` (sibling of `com.acme.mod` under
`src/test/resources/crossmodule/`): `module-info.java` with
`requires io.github.lamspace.openproxy;`, `Widget`, `LookupHolder`, and a `ProxyDriver`
that builds an interceptor and calls `OpenProxy.proxy(...)` **from inside the layer**.
Reflection from the classpath test into the driver is mandatory, not cosmetic: the
layer gets its own copy of `Interceptor` etc. (the J lesson), so a classpath-created
interceptor would be an argument type mismatch, and compiling the driver requires the
synthesized openproxy jar on javac's `--module-path`.

**D5: Measure before documenting the ASM edge.** Task 1.1 answers whether
`--module-path openproxy.jar:asm.jar` plus an app `requires openproxy` resolves ASM
(automatic modules auto-require other *automatic* modules; ASM 9.7.1 ships a real
`module-info` and is *named*). Whichever way it goes, the guide text records the exact
working launch shape; the packaging decision (D1) does not change with the answer.

**D5 measured outcome (tasks 1.1/1.2, 2026-10-02, `/tmp/opx-p3-spike`):**

- 1.1 — an automatic module does NOT pull the named ASM module into the graph:
  `requires io.github.lamspace.openproxy` alone dies at first generation with
  `NoClassDefFoundError: org/objectweb/asm/Type`; with `--add-modules
  org.objectweb.asm` ASM resolves, the `canRead` pre-check passes, and the hidden
  class DEFINES successfully inside the target module — readability was indeed the
  whole story D1 predicted. A second, previously unreachable gate then surfaces at
  instantiation: `OpenProxy.instantiateProxy` uses `Constructor.newInstance`
  (`OpenProxy.java:962`) and the library module cannot reflectively access the
  generated class living in the target's unexported package
  (`... does not export com.acme.app to module io.github.lamspace.openproxy`).
  The generated proxy class and its constructor are always `ACC_PUBLIC`
  (`ClassGenerator.java:153`, `:307`), so two mechanisms clear this gate:
  (a) user-side qualified `exports <target-pkg> to io.github.lamspace.openproxy;`
  — measured end-to-end green, intercept + invokeSuper included;
  (b) library-side instantiation through the supplied lookup
  (`lookup.findConstructor(hiddenClass, ...).invoke(...)`) — micro-measured green
  against a hidden class in an UNexported package.
- 1.2 — today's `--add-reads <module>=ALL-UNNAMED` workaround fixes the pre-check
  and definition but hits the same instantiation gate from the unnamed side; the
  complete classpath workaround is `--add-reads` AND
  `--add-exports <module>/<pkg>=ALL-UNNAMED` (measured green).

**D6 (settled 2026-10-02 with the partner): mechanism (b), library-side instantiation
through the supplied lookup; (a) is documented as the fallback shape.**
`instantiateProxy` SHALL, when the call supplied a lookup, create the instance via
`lookup.findConstructor(proxyClass, ctorType).invokeWithArguments(initArgs)` instead
of `Class.getConstructor(...).newInstance(...)`; the no-lookup default paths keep the
reflection shape untouched (they never hit the gate: the generated class is accessible
from the library's own context there). Chosen because the D1/D3 capability model
already says the caller grants "loader + package + privilege" — using that privilege
to instantiate is consistent, and it keeps the user-side contract at plain `requires`
(plus the ASM launch shape). Alternative (a), qualified
`exports <pkg> to io.github.lamspace.openproxy;`, measured green end-to-end and is
kept as a documented shape for deployments that pin an older library; it fails nothing
but imposes package exposure on plugin internals. Consequence for the spec: success
requires no target-package export, and the scenario WHEN says so explicitly.
Exception semantics note: `invokeWithArguments` throws the target exception directly
rather than wrapping in `InvocationTargetException`; instantiation failures remain
wrapped by the existing `Failed to create proxy` RuntimeException path, so observable
error behavior on failure is unchanged for callers.

## Risks / Trade-offs

- [Automatic modules export `internal`/`generator` on the module path] → accepted:
  the generated bytecode references them (Context table), so any modular packaging
  must export them too; the name stays a convention signal.
- [Two OpenProxy copies in one JVM (classpath test copy + module copy in the layer)
  confuse readers] → the driver-inside-the-layer design makes the intent explicit and
  mirrors the documented G/J loader-copy rules.
- [Diagnostic wording change breaks a user parsing the message] → message text is not
  contract; the spec scenario pins only the module names and the readability statement,
  both retained.
- [Synthesized jar in tests drifts from the real build artifact] → the manifest
  attribute is the only shipped difference from `target/classes`; the build check
  (task 2.2) compares the real `mvn package` output against the pre-change jar to pin
  that.
- [Task 1.1 measures that ASM never enters the graph in common shapes] → revisit
  condition in D1; docs carry the workaround meanwhile.

## Migration Plan

Purely additive for module-path users; invisible to classpath users. Ship in 0.2.0
alongside the P0 bump: CHANGELOG entry, README JPMS paragraph,
`docs/guide/11-jpms*.md` limit section → `requires` recipe, ROADMAP P3 closed and
"not proxyable until ..." wording retired. Rollback is a manifest revert; nothing in
class metadata changes either way.
