# Proposal

## Why

A target inside a named JPMS module cannot be proxied: OpenProxy ships as a classpath
artifact (unnamed module), and a named module can never read the unnamed module.
Measured in `archive/2026-10-01-support-cross-classloader-proxy` (task 1.1): a public
class defined through a full-privilege `privateLookupIn` from inside its own module
links into the module, then fails the superinterface check with
`IllegalAccessError ... because module com.acme.mod cannot read unnamed module`.
The lookup plumbing, validation and the `canRead` pre-check are already in place
(`OpenProxy.java` `requireContractTypesVisible`); the only missing piece is a module
declaration that the target module can `requires` — the residual tracked as
ROADMAP P3.

## What Changes

- The published jar declares `Automatic-Module-Name: io.github.lamspace.openproxy`
  (maven-jar-plugin manifest entry), so the artifact becomes an automatic module when
  placed on the module path. Automatic modules export all packages, which covers every
  package generated proxy bytecode references (`io.github.lamspace`,
  `io.github.lamspace.internal`, `io.github.lamspace.generator`).
- Targets in a named module become proxyable through the existing seven supplied-lookup
  entry points once the target module `requires` the library and openproxy + ASM sit on
  the module path. No new API surface, no change to any generated class on classpath
  deployments.
- **Measured addition (task 1.1):** once readability is fixed, instantiation is the
  next gate — the library's `Constructor.newInstance` cannot reflect into the target's
  unexported package. Supplied-lookup calls will instantiate through that lookup's
  own privilege (`findConstructor`), so the user-side contract stays plain `requires`
  with no package exports; no-lookup default paths are untouched.
- The readability diagnostic message in `CrossLoaderDiagnostics.forModuleRead` is
  rewritten: the stale "until OpenProxy itself ships a module declaration" sentence
  becomes the actionable remedy (place the jars on the module path, add
  `requires io.github.lamspace.openproxy;`). Classpath deployments keep failing fast
  with the same `IllegalArgumentException`, no `LinkageError` escapes.
- Docs: JPMS paragraphs in `README.md` / `README_CN.md` and `docs/guide/11-jpms*.md`,
  `CHANGELOG.md` (rides the pending 0.2.0 bump tracked as ROADMAP P0), and the P3
  section of `ROADMAP.md` closes.

## Capabilities

### New Capabilities

- `jpms-module-deployment`: the published artifact's module-path identity
  (stable automatic module name) and the proxyability of named-module targets whose
  module `requires` the library, including the preserved fail-fast diagnostic for
  classpath deployments.

## Impact

- `pom.xml`: maven-jar-plugin manifest configuration (pinned version, project style).
- `src/main/java/io/github/lamspace/internal/CrossLoaderDiagnostics.java`: message text
  of `forModuleRead` only; no control-flow change — the existing `canRead` pre-check is
  the gate that starts passing under module-path deployment.
- `src/main/java/io/github/lamspace/OpenProxy.java`: `instantiateProxy` gains a
  supplied-lookup branch (`findConstructor(...).invokeWithArguments(...)`); the
  no-lookup default path keeps `getConstructor().newInstance()`.
- Tests: `CrossClassLoaderProxyTest.namedModuleTargetIsDiagnosed...` keeps passing
  (it asserts `cannot read module` + the module name, both retained in the new text);
  new module-graph fixtures extend `NamedModuleFixture` with a real `requires` edge.
- No change to generated bytecode, dispatch, caching identity, eviction, or any
  classpath behavior; the 0.1.0 benchmark numbers stay valid.
- Risk to measure before implementing (not assumed): whether the named ASM module
  (`org.objectweb.asm`, verified to ship a real `module-info`) enters the module graph
  when only `io.github.lamspace.openproxy` is required, and whether
  `--add-reads <module>=ALL-UNNAMED` works around the limitation today. Both outcomes
  land in the docs, not in the packaging choice.
