# Proposal

## Why

Hot-deploying frameworks (OSGi bundles, Spring DevTools restart loaders, plugin systems) own their target classes in a child `ClassLoader`, so OpenProxy cannot proxy them at all today: every shape fails at `Lookup.defineHiddenClass` (class proxies, package-private interface proxies) or at link time with `NoClassDefFoundError` (public interface proxies) — the lookup class `io.github.lamspace.internal.LookupManager` is not in the target's loader, and `defineHiddenClass` requires a full-privilege lookup whose class shares the target's loader and package.

The only current workaround is to load a private copy of OpenProxy into the plugin loader. Measured on `openproxy-0.1.0`/JDK 25 it works when everything is loader-consistent, but it duplicates library state (per-copy `WeakCache`, per-copy dispatch counters, per-copy static fields for `proxyStatic`) and it breaks the moment a framework hands the copy an interceptor created by the parent loader — `IllegalArgumentException: argument type mismatch`.

A spike proved the fix is mechanically available **without `Unsafe`, custom `ClassLoader`s, or JDK internal APIs**: generate the bytecode with the normal generators in OpenProxy's loader, then define the hidden class with a full-privilege lookup whose class lives in the *target's* loader. Parent-generated bytes defined that way load, resolve `io.github.lamspace.Interceptor` / `DispatchTarget` / `Rebindable` through ordinary parent delegation to the same `Class` objects, instantiate, and `invokeSuper` works (`Hello, K`). The missing piece is only a way for a caller to hand OpenProxy that lookup.

## What Changes

- Add a cooperative **definer hook**: an optional caller-supplied object that performs hidden-class definition using a lookup rooted in the target's loader. OpenProxy keeps generating bytecode; the hook only decides *where* the class is defined. Exact type and parameter shape are for `design.md`; the API is additive overloads on the existing `proxy(...)` family (plus the interface-array form), so no existing signature changes.
- Make the all-public interface path loader-aware: keep defining in `io.github.lamspace` with `MethodHandles.lookup()` when the interfaces are resolvable from OpenProxy's loader (this is what lets public JDK interfaces in strongly-encapsulated modules work without `--add-opens`), and route to the target's loader only when they are not — instead of failing with `NoClassDefFoundError`.
- Include the definer in the proxy-class cache key, so two definers over the same target `Class` do not share one generated class, and eviction can be scoped to the loader that actually owns the class.
- Same-loader behavior is byte-for-byte unchanged: the default path keeps using `LookupManager.getLookup(target)` / `MethodHandles.lookup()` exactly as today, so all existing benchmarks and the 3-5x-over-CGLib claim are unaffected.
- Cross-loader regression tests flip from "fails with the actionable diagnostic" (added by `clarify-cross-classloader-proxy-limits`) to "proxies and delegates correctly", plus a hot-deploy test: sibling loaders, independent regeneration, old instances still serving, `evictClassLoader` scoping.

## Capabilities

### New Capabilities

- `cross-classloader-proxy`: caller-supplied hidden-class definition rooted in the target's loader, enabling proxies for targets owned by a different loader than OpenProxy, with definer-aware caching and eviction.

### Modified Capabilities

- `non-public-interface-proxy`: qualify the "All-public path unchanged" requirement. The `io.github.lamspace` + `MethodHandles.lookup()` guarantee holds only while the interfaces are visible from OpenProxy's loader; a loader-invisible public interface must define in the target's loader rather than fail to link. The strongly-encapsulated-JDK-interface scenario must keep passing unchanged.
- `openproxy-core`: relax the "Hidden class loading" requirement from "a single code path based on `Lookup.defineHiddenClass(byte[], true)`" to allow the *lookup source* to be supplied by the caller, while keeping the commitments that matter: still `defineHiddenClass`, still no custom `ClassLoader`, still GC-eligible proxy classes.
- `hot-reload`: state that hot deployment across loaders is supported when a definer is supplied, and define how `evict` / `evictClassLoader` interact with definer-scoped cache keys.

## Impact

- `src/main/java/io/github/lamspace/OpenProxy.java` — `generateProxyClass` (lines ~285-330) gains the definition-strategy branch; `proxy(...)` overloads and `CacheParams` (lines ~100-143) carry the definer; `instantiateProxy` unchanged.
- `src/main/java/io/github/lamspace/internal/LookupManager.java` — split "obtain a lookup" from "define with it", or be replaced by the definer at the definition site.
- New public type for the hook (name TBD in design) — a new API surface element on a young 0.1.0 artifact, accepted since the version has just shipped.
- `src/main/java/io/github/lamspace/generator/*` — expected unchanged; if the all-public interface path needs a package-name change for loader-invisible interfaces, `InterfaceGenerator` is touched and its byte-for-byte claim must be re-verified against `ProxyBenchmark`.
- `WeakCache` / `evict` / `evictClassLoader` semantics with definer-aware keys; `docs/guide/10-hot-reload*.md`, `11-jpms*.md`, `09-multi-interface-proxy*.md`, `ROADMAP.md`, `CHANGELOG.md`.
- Risk: medium. JPMS-sensitive on both sides (a definer in a *named* module still needs its package open to be usable), and the JDK-public-interface guarantee is the most likely regression — `PublicJdkInterfaceProxyTest` and `JpmsStrongEncapsulationTest` are the guard rails.
- Depends-on: `clarify-cross-classloader-proxy-limits` (its diagnostic and test scaffolding is what this change flips). Out of scope: internal bridge-class injection via `Unsafe.defineClass` or similar — rejected because it needs no caller cooperation but drags the library into JDK internal APIs, contrary to the stance set by `e164ad4` and `docs/guide/11-jpms.md`.
