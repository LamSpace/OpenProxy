## Purpose

Lets a framework proxy target classes owned by a class loader that cannot be seen from the library's own loader, by having the caller supply the lookup that defines the generated class.

## Requirements

### Requirement: Caller-supplied definition lookup

The system SHALL accept an optional caller-supplied `java.lang.invoke.MethodHandles.Lookup` at each proxy entry point (`proxy` for a concrete class, `proxy` for an interface array, `intercept`, and `proxyStatic`), and SHALL define the generated hidden class with that lookup instead of its own. The generated proxy class SHALL live in the package of the supplied lookup's class, so that the JVM requirement that a hidden class share its lookup class's package is satisfied without the caller arranging package names.

The supplied lookup MUST have full privilege access; when it does not (for example its class is in a different loader than the target, or a different package than the generated class requires), the system SHALL reject the call with an `IllegalArgumentException` naming the lookup class, its package and loader, and the target's loader — not by letting a `java.lang.IllegalAccessException` escape.

#### Scenario: Class proxy of a child-loader target

- **WHEN** a concrete class is loaded by a child loader that the library's loader cannot see
- **AND** the caller supplies a lookup whose class was loaded by that child loader and has private access in the target's package
- **THEN** `proxy(...)` returns a proxy whose class is defined by the child loader
- **AND** `invokeSuper` runs the target's real implementation

#### Scenario: Public interface invisible to the library's loader

- **WHEN** a `public` interface is owned by a child loader the library's loader cannot see
- **AND** the caller supplies a lookup rooted in that child loader
- **THEN** the proxy implements that exact interface (same `Class` object) instead of failing to link with `NoClassDefFoundError`

#### Scenario: Package name follows the supplied lookup

- **WHEN** a proxy is generated with a caller-supplied lookup whose class is in package `com.acme`
- **THEN** the generated proxy class is in package `com.acme`
- **AND** the same request with a lookup whose class is in another package either succeeds in that package or is rejected by the validation above

#### Scenario: Lookup lacking private access is rejected with a clear reason

- **WHEN** the supplied lookup's class is loaded by a different loader than the target
- **THEN** the call fails with `IllegalArgumentException` identifying the lookup class, its loader, and the target's loader

#### Scenario: Loader that cannot see the library reports the visibility gap

- **WHEN** the target's loader cannot resolve the library's own types (it neither delegates to the library's loader nor has its own copy)
- **THEN** the call fails with a diagnostic naming the two loaders and stating that the target's loader must resolve the library's types
- **AND** no bare `NoClassDefFoundError` for a library type reaches the caller

#### Scenario: Named-module target is rejected with the readability reason

- **WHEN** the target type and the supplied lookup live in a named module that cannot read the module owning the library's contract types
- **THEN** the call fails with an `IllegalArgumentException` naming both modules and stating that the target's module must read the library's module
- **AND** no `IllegalAccessError` or other `LinkageError` escapes from class definition

### Requirement: Per-lookup proxy caching

The system SHALL treat the supplied lookup as part of the proxy-class cache identity, so that two different lookups for the same target never share one cached proxy class, and the same lookup for the same target reuses one cached class.

#### Scenario: Different lookups do not share a cached class

- **WHEN** the same target class is proxied twice with two lookups whose classes differ
- **THEN** two distinct generated classes are produced

#### Scenario: Same lookup reuses the cached class

- **WHEN** the same target is proxied twice with an equal lookup
- **THEN** the second call returns an instance of the same generated class without regenerating bytecode

### Requirement: Same-loader defaults unchanged

The system SHALL keep the existing definition strategy, generated bytecode, and package placement byte-for-byte unchanged for every call that does not supply a lookup, including the all-public interface path that uses the library's own lookup and the non-public interface anchor path.

#### Scenario: Unaffected callers see identical behavior

- **WHEN** a proxy is requested without a supplied lookup
- **THEN** the generated class is placed and defined exactly as before
- **AND** interception performance and the published benchmark results are unchanged
